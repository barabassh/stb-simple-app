правила, по которым она расширяется (раздел 7), модели этапа 2 (раздел 8) и этапа 3 (раздел 9).

## 2. Пользователь

```prisma
model User {
  id                 String    @id @default(cuid())
  login              String    @unique              // хранится в нижнем регистре
  fullName           String
  position           String?
  email              String?   @unique
  phone              String?
  comment            String?

  passwordHash       String
  role               Role      @default(EMPLOYEE)
  isActive           Boolean   @default(true)

  lastLoginAt        DateTime?
  failedLoginCount   Int       @default(0)
  lockedUntil        DateTime?

  createdAt          DateTime  @default(now())
  updatedAt          DateTime  @updatedAt
  createdById        String?
  updatedById        String?

  sessions           Session[]
  auditLogs          AuditLog[] @relation("AuditActor")

  createdBy          User?     @relation("UserCreatedBy", fields: [createdById], references: [id], onDelete: SetNull)
  createdUsers       User[]    @relation("UserCreatedBy")
  updatedBy          User?     @relation("UserUpdatedBy", fields: [updatedById], references: [id], onDelete: SetNull)
  updatedUsers       User[]    @relation("UserUpdatedBy")

  @@index([role])
  @@index([isActive])
  @@index([fullName])
}
```

**Пояснения к решениям:**

- `login` приводится к нижнему регистру **до записи**. Уникальный индекс
  PostgreSQL чувствителен к регистру, поэтому без нормализации `Ivanov` и
  `ivanov` окажутся разными учётными записями. Нормализация выполняется в
  схеме Zod, а не в базе.
- Пользователь не удаляется — ни жёстко, ни мягко, поэтому поля `deletedAt`
  у модели нет. Доступ закрывается деактивацией (`isActive = false`), запись
  со всей историей остаётся (`ТЗ.md`, п. 4.7). Ссылки из журнала аудита и из
  будущих таблиц (автор проекта, ответственный за смету) не разрушаются, а
  логин и email навсегда закреплены за одним человеком: уникальные индексы
  действуют среди всех записей, включая неактивные.
- `email` приводится к нижнему регистру в схеме Zod по той же причине, что и `login`.
- Признака обязательной смены пароля нет: пароли назначает и сбрасывает только
  администратор, пользователь свой пароль не меняет (`ТЗ.md`, п. 3.3).
- `failedLoginCount` и `lockedUntil` реализуют требование ТЗ п. 3.3 —
  блокировка на 15 минут после 5 неудач.
- Связи `createdBy`/`updatedBy` объявлены как `SetNull`, как и `AuditLog.actor`.
  Пользователи не удаляются, поэтому на практике ссылки не обнуляются; читаемый
  логин автора в журнале всё равно хранится отдельно (см. ниже).

## 3. Сессия

```prisma
model Session {
  id           String    @id @default(cuid())
  userId       String
  tokenHash    String    @unique          // SHA-256 от токена, сам токен не хранится
  expiresAt    DateTime
  lastActiveAt DateTime  @default(now())
  ip           String?
  userAgent    String?
  createdAt    DateTime  @default(now())
  revokedAt    DateTime?

  user         User      @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@index([expiresAt])
}
```

В базе лежит только хэш токена: утечка дампа базы не должна давать возможность
войти под чужой сессией. Сессия считается действительной, если
`revokedAt = null` и `expiresAt > now()`.

Отзыв сессий происходит при деактивации пользователя, сбросе пароля
администратором и по кнопке «Завершить сессию». Истёкшие записи пользователя удаляются при его
входе, перед созданием новой сессии (`createSession` в `src/lib/auth/session.ts`).

## 4. Журнал аудита

```prisma
model AuditLog {
  id         String      @id @default(cuid())
  at         DateTime    @default(now())

  actorId    String?
  actorLogin String                        // дублируется строкой намеренно
  action     AuditAction
  entity     String                        // "User", "Session", "Project", ...
  entityId   String?
  summary    String                        // читаемое описание для списка
  changes    Json?                         // [{ field, before, after }]
  ip         String?
  userAgent  String?

  actor      User?       @relation("AuditActor", fields: [actorId], references: [id], onDelete: SetNull)

  @@index([at])
  @@index([entity, entityId])
  @@index([actorId, at])
  @@index([action])
}
```

**Ключевые решения:**

- `actorLogin` хранится строкой рядом с `actorId`: запись журнала читается
  сама по себе, без соединения с таблицей пользователей (`ТЗ.md`, п. 4.9).
- `actorId` необязателен: события `LOGIN_FAILED` возникают до того, как известен
  пользователь, — там заполняется только `actorLogin` с введённым значением.
- `entity` + `entityId` делают журнал универсальным: проекты и сметы следующих
  этапов подключаются без изменения таблицы.
- `changes` — массив в `jsonb`. Отдельная таблица изменений дала бы более строгую
  структуру, но журнал только пишется и читается целиком, поэтому дополнительные
  соединения и индексы не нужны.
- Записи журнала не изменяются и не удаляются. В приложении нет ни одного пути,
  который бы их правил.

### 4.1 Что запрещено записывать

Значения полей `passwordHash`, `password`, `newPassword`, `tokenHash` в `changes`
не попадают ни при каких условиях. Список задаётся явной константой в
`src/lib/audit`, а не эвристикой по названию поля: правило «поле содержит
`password`» рано или поздно пропустит `secretKey` или `apiToken`.

Сброс пароля журналируется как факт: `action = PASSWORD_CHANGE`,
`changes = null`.

### 4.2 Вычисление изменений

Изменения вычисляются сравнением состояния «до» и «после» в пределах одной
транзакции с самим изменением. Поля, значения которых не поменялись, в `changes`
не попадают. Ссылочные поля пишутся читаемым значением (не идентификатор роли,
а её название), иначе журнал бесполезен без ручной расшифровки.

### 4.3 События этапа 1

| Событие | `action` | `entity` / `entityId` | `changes` |
|---|---|---|---|
| Вход | `LOGIN` | `Session` / новая сессия | — |
| Неудачная попытка входа | `LOGIN_FAILED` | `Session` / — | — |
| Выход | `LOGOUT` | `Session` / завершённая сессия | — |
| Создание пользователя | `CREATE` | `User` / пользователь | заполненные поля |
| Изменение данных, в том числе своего профиля | `UPDATE` | `User` / пользователь | изменённые поля, кроме роли и статуса |
| Смена роли | `ROLE_CHANGE` | `User` / пользователь | `role` |
| Деактивация, активация | `STATUS_CHANGE` | `User` / пользователь | `isActive` |
| Сброс пароля | `PASSWORD_CHANGE` | `User` / пользователь | — |
| Завершение сессии администратором или самим пользователем в профиле | `SESSION_REVOKE` | `User` / владелец сессии | — |
| Выгрузка в Excel, PDF или печатное представление | `EXPORT` | `User` — реестр пользователей, `AuditLog` — журнал аудита / — | — |

- У `LOGIN_FAILED` поле `actorId` пустое, `actorLogin` — введённый логин; причина отказа
  (логин не найден, учётная запись деактивирована, неверный пароль, блокировка) видна
  только в `summary` — форма входа по-прежнему показывает единый текст.
- Одно сохранение формы, изменившее и данные, и роль, и статус, даёт до трёх записей
  в одной транзакции: фильтр журнала по `ROLE_CHANGE` находит смену роли независимо
  от того, каким экраном она сделана. Сохранение без изменений ничего не пишет.
- Действие, которое ничего не изменило (повторный отзыв уже завершённой сессии),
  в журнал не попадает.
- Текущую сессию в профиле не завершают: это выход, он пишется как `LOGOUT`.
  «Завершить все, кроме текущей» даёт одну запись `SESSION_REVOKE`.
- Вкладка «История изменений» в карточке пользователя — записи с `entity = "User"`
  и `entityId` этого пользователя (право `users.history.read`); входы и выходы видны
  в журнале по автору.
- `summary` читают и те, кому IP-адреса недоступны, поэтому в нём нет IP-адресов:
  завершённая администратором сессия названа только браузером.
- `summary` выгрузки называет отчёт, формат и число строк: «Выгрузка «Реестр
  пользователей» (Excel), строк: 12». Выгрузка, отклонённая по правам, не пишется —
  данные никому не переданы.

## 6. Начальные данные

Сид (`prisma/seed.ts`) создаёт единственную запись: администратора `admin` с
паролем из переменной окружения `SEED_ADMIN_PASSWORD`. Пароля по умолчанию в коде нет — при отсутствии
переменной сид завершается с ошибкой. Повторный запуск сида не создаёт дубликат.

## 7. Правила расширения схемы

Соглашения, обязательные для всех моделей следующих этапов:

1. Идентификатор — `String @id @default(cuid())`.
2. Обязательные поля: `createdAt`, `updatedAt`, `createdById`, `updatedById`.
   Их отсутствие означает, что отметку «кем и когда изменено» придётся
   добавлять задним числом по всей базе.
3. Удаление — мягкое, через `deletedAt`, если на запись могут ссылаться другие
   таблицы или журнал. Исключение — пользователи: они не удаляются вовсе,
   только деактивируются (раздел 2).
4. Денежные суммы — `Decimal @db.Decimal(14, 2)`. `Float` для денег недопустим.
5. Даты хранятся в UTC; перевод в `Europe/Kyiv` выполняется при отображении.
6. Любое изменение схемы оформляется миграцией
   (`npx prisma migrate dev --name ...`). Применённые миграции не редактируются.
7. Новая сущность сразу подключается к аудиту: значение `entity` — имя модели.

### 8.3 Пояснения к решениям

- **Обязательно только `legalName`** (`ТЗ.md`, п. 5.4). Адрес офиса и почтовый адрес
  записываются, только если заполнены целиком (это проверяет схема Zod); склад и строки
  телефонов, соцсетей и видов деятельности сохраняются такими, как введены, поэтому их поля
  в базе допускают `NULL`. Полностью пустые строки не сохраняются.
- **Одна запись.** Уникальное поле `singleton` с единственным допустимым значением `true`
  не даёт создать вторую запись даже при двух одновременных первых сохранениях: второе
  получит нарушение уникальности, а не дубликат. Значение `true` закрепляется ограничением
  `CHECK ("singleton" = true)`, которое дописывается в SQL миграции, созданной с
  `--create-only`, до её применения — Prisma такие ограничения не описывает.
- **Один офис и один почтовый адрес.** Частичный уникальный индекс, тоже дописанный
  в SQL миграции: `UNIQUE ("companyId", "type") WHERE "type" IN ('OFFICE', 'POSTAL')
  AND "deletedAt" IS NULL`. Склады ограничиваются десятью в схеме Zod.
- **Адреса — отдельные записи с полями аудита и мягким удалением.** На склады будут
  ссылаться проекты и поставки следующих этапов, поэтому адрес при правке обновляется
  на месте (форма передаёт его `id`), а удалённый склад получает `deletedAt`. Выборки
  исключают записи с `deletedAt`.
- **Телефоны, социальные сети и виды деятельности — части записи о компании**, а не
  самостоятельные сущности: на них ничто не ссылается, и меняются они только вместе
  со всей формой. Поэтому при сохранении они заменяются целиком в той же транзакции,
  без собственных `createdAt`/`updatedById` и без `deletedAt`, — это сознательное
  исключение из правил 2 и 3 раздела 7. Кто и когда их изменил, видно по отметкам
  `CompanyProfile` и журналу, где каждый список записан «было → стало».
- **`version`** увеличивается при каждом сохранении с изменениями. Форма отправляет
  версию, с которой открылась; обновление выполняется условием
  `where: { id, version }` и при нуле обновлённых строк возвращает ошибку одновременной
  правки. Сравнение по `updatedAt` не используется: у отметки времени есть точность,
  а у счётчика — нет.
- **`registeredOn` — только дата** (`@db.Date`), без времени и часового пояса: переводить
  её в `Europe/Kyiv` нельзя, иначе дата сдвигается. Форматируется как дата UTC.
- **Номера хранятся нормализованными** (без пробелов и точек, в верхнем регистре),
  телефон — в международном виде `+31…`, индекс Нидерландов — `1234 AB`. Нормализация
  выполняется в схеме Zod, как у логина пользователей.
- Денежных полей нет.

### 8.4 События аудита этапа 2

| Событие | `action` | `entity` / `entityId` | `changes` |
|---|---|---|---|
| Первое заполнение сведений о компании | `CREATE` | `CompanyProfile` / запись | заполненные поля |
| Изменение сведений о компании | `UPDATE` | `CompanyProfile` / запись | изменённые поля |

- `"CompanyProfile"` добавляется в `AUDIT_ENTITIES` (`src/lib/audit`).
- Адреса, телефоны, социальные сети и виды деятельности отдельных записей журнала
  не получают: всё сохранение формы — одна запись `CompanyProfile`. Поля `changes`:
  `officeAddress`, `postalAddress`, `warehouses`, `phones`, `socialLinks`, `activities` —
  читаемой строкой (`ТЗ.md`, п. 5.8); служебные `version`, `singleton`, `sortOrder`
  и идентификаторы в `changes` не попадают.
- `summary`: «Заполнены сведения о компании» / «Изменены сведения о компании».

### 8.5 Диаграмма связей этапа 2

```
CompanyProfile ──< CompanyAddress     офис, почтовый, склады (мягкое удаление)
CompanyProfile ──< CompanyPhone       дополнительные телефоны
CompanyProfile ──< CompanySocialLink  социальные сети
CompanyProfile ──< CompanyActivity    виды деятельности SBI
User ──< CompanyProfile, CompanyAddress   createdBy / updatedBy (SetNull)
```

### 9.2 Модели

```prisma
model Customer {
  id                  String        @id @default(cuid())
  type                CustomerType  @default(COMPANY)
  name                String                               // название компании или ФИО
  kvkNumber           String?       @unique                // только COMPANY
  vatId               String?                              // только COMPANY
  contactPerson       String?                              // только COMPANY
  email               String?

  street              String?
  houseNumber         Int?
  houseNumberAddition String?
  postcode            String?
  city                String?
  country             String?       @db.Char(2)            // заполнен вместе с адресом

  isActive            Boolean       @default(true)         // false — в архиве
```

### 9.3 Пояснения к решениям

- **Заказчики и подрядчики не удаляются, а архивируются** (`isActive`), как пользователи,
  поэтому `deletedAt` у них нет — это исключение из правила 3 раздела 7. На них ссылаются
  проекты, журнал и (у подрядчика) учётные записи; архивная запись остаётся видимой в старых
  проектах, но не предлагается в формах. Связи на них — `Restrict`: запись, на которую
  ссылаются, нельзя удалить и в обход приложения.
- **Поля по виду заказчика.** У частного лица `kvkNumber`, `vatId` и `contactPerson` всегда
  `NULL`: схема Zod обнуляет их при `type = PERSON`, а ограничение
  `CHECK ("type" = 'COMPANY' OR ("kvkNumber" IS NULL AND "vatId" IS NULL AND "contactPerson" IS NULL))`
  дописывается в SQL миграции.
- **`kvkNumber` уникален** обычным индексом: в PostgreSQL несколько `NULL` уникальность
  не нарушают. Номер хранится нормализованным (раздел 8.3), поэтому учитывать регистр
  при сравнении не нужно. Уникальность у заказчиков и у подрядчиков раздельная: одна
  организация может быть и тем, и другим.
- **Адрес колонками в записи**, а не ссылкой на `CompanyAddress`: адрес заказчика, подрядчика
  и объекта принадлежит только своей записи и меняется вместе с ней. Правила полей те же,
  что у адреса офиса (`ТЗ.md`, п. 5.4). У справочников адрес необязателен, и `country`
  заполнен, только когда заполнен адрес; у проекта адрес обязателен.
- **Номер проекта** уникален среди неудалённых проектов без учёта регистра — частичным
  уникальным индексом, дописанным в SQL миграции:
  `CREATE UNIQUE INDEX "Project_number_active_key" ON "Project" (lower("number")) WHERE "deletedAt" IS NULL`.
  Удалённый проект освобождает номер. Нарушение индекса при сохранении превращается
  в ошибку поля «Проект с таким номером уже есть».
- **Предлагаемый номер** вычисляется выборкой наибольшего числового хвоста среди номеров
  вида `ГГГГ-число` текущего года, включая удалённые проекты, и не резервируется
  (`ТЗ.md`, п. 6.6). Отдельной таблицы-счётчика нет: номер можно править вручную, поэтому
  счётчик всё равно не гарантировал бы, что номер свободен.
- **Бюджет:** хранятся `budgetAmount` без НДС и `vatRate`; сумма с НДС вычисляется при
  показе и выгрузке и не хранится — иначе её пришлось бы согласовывать при каждой правке.
  Ограничение `CHECK ("budgetAmount" IS NULL OR "vatRate" IS NOT NULL)` дописывается в SQL
  миграции. Часы — `Decimal`, а не `Float`, по той же причине, что и деньги.
- **Статус и закрытие:** `closedAt` заполнен ровно у закрытого проекта —
  `CHECK (("status" = 'CLOSED') = ("closedAt" IS NOT NULL))` в SQL миграции. Запрет изменений
  закрытого проекта выполняется условием записи
  `updateMany({ where: { id, status: "IN_PROGRESS", deletedAt: null } })`; ноль обновлённых
  строк — ошибка «Проект закрыт». Проверки статуса перед записью недостаточно: проект могут
  закрыть между чтением и записью. Этапы 4 и 5 проверяют статус проекта так же — в транзакции
  записи отчёта или расхода.
- **`startDate` — только дата** (`@db.Date`), как `registeredOn` в разделе 8.3: форматируется
  как дата UTC. Длительность не хранится: она вычисляется от `startDate` до сегодняшней даты
  по `Europe/Kyiv` или до даты `closedAt` по `Europe/Kyiv`.
- **Удаление проекта мягкое** (`deletedAt`), все выборки проектов исключают удалённые.
  Закрытый проект не удаляется: условие `status = IN_PROGRESS` входит в запись удаления.
- **Привязка подрядчика** `User.contractorId` заполняется только у роли `CONTRACTOR`; при смене
  роли действие обнуляет поле в той же транзакции. Ограничение в базе не вводится: роль
  и привязка меняются одной формой, правило проверяют схема Zod и действие.

### 9.4 События аудита этапа 3

| Событие | `action` | `entity` / `entityId` | `changes` |
|---|---|---|---|
| Создание заказчика, подрядчика, проекта | `CREATE` | `Customer`, `Contractor`, `Project` / запись | заполненные поля |
| Изменение заказчика, подрядчика, проекта | `UPDATE` | то же | изменённые поля, кроме статуса |
| Архив и восстановление заказчика, подрядчика | `STATUS_CHANGE` | `Customer`, `Contractor` / запись | `isActive`: «Активен» / «В архиве» |
| Закрытие проекта, возврат в работу | `STATUS_CHANGE` | `Project` / проект | `status`: «В работе» / «Закрыт» |
| Удаление проекта | `DELETE` | `Project` / проект | — |
| Привязка учётной записи к подрядчику | `UPDATE` | `User` / пользователь | `contractor`: название подрядчика |
| Выгрузка реестра | `EXPORT` | `Customer`, `Contractor`, `Project` / — | — |

- `"Customer"`, `"Contractor"`, `"Project"` добавляются в `AUDIT_ENTITIES` с названиями
  «Заказчик», «Подрядчик», «Проект».
- Адрес пишется одним полем `address` одной строкой, заказчик проекта — полем `customer`
  с названием, ставка НДС — названием, суммы и часы — строкой в формате чисел приложения,
  `startDate` — `dd.MM.yyyy`. `closedAt`, `closedById`, `deletedAt` и идентификаторы в `changes`
  не попадают.
- **Бюджет в журнале.** Поля `budgetAmount`, `vatRate`, `budgetHours` пишутся в `changes`
  как обычно, но выборка истории и журнала для пользователя без `projects.budget.read`
  заменяет их одной строкой «Бюджет: изменён» без значений (`ТЗ.md`, п. 6.10). Список полей
  бюджета задаётся явной константой рядом с выборкой журнала — так же, как список
  исключаемых полей из раздела 4.1.
- `summary` называет запись номером и названием проекта или названием заказчика и подрядчика
  и не содержит сумм.

### 9.5 Диаграмма связей этапа 3

```
Customer ──< Project            заказчик проекта (Restrict)
Contractor ──< User             учётные записи подрядчика (Restrict)
User ──< Project                closedBy, createdBy / updatedBy (SetNull)
User ──< Customer, Contractor   createdBy / updatedBy (SetNull)
```
