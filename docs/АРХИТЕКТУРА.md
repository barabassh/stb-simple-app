# Архитектура ConstructionProjects

Документ фиксирует стек, структуру проекта и соглашения. Требования к
функциональности — в `ТЗ.md`.

## 1. Стек и обоснование

| Слой | Выбор | Почему |
|---|---|---|
| Каркас | Next.js 15, App Router | Один проект вместо пары «фронтенд + API». Server actions убирают ручной слой REST-эндпоинтов для форм. Серверный рендеринг даёт быстрые тяжёлые реестры |
| Язык | TypeScript, режим `strict` | Типы схемы Prisma доходят до компонентов без ручного дублирования |
| База | PostgreSQL 16 | Оконные функции и агрегаты для будущего дашборда, тип `jsonb` для журнала изменений, честный `Decimal` для денег |
| ORM | Prisma | Типобезопасные запросы, версионируемые миграции, читаемая схема как документация модели |
| Стили | Tailwind CSS | Скорость вёрстки без разрастания CSS-файлов |
| Компоненты | shadcn/ui (Radix) | Код компонентов лежит в репозитории и правится под себя; доступность «из коробки» |
| Таблицы | TanStack Table | Серверная сортировка и пагинация, фиксированные колонки, большие объёмы строк |
| Формы | react-hook-form + Zod | Одна схема валидации работает и на клиенте, и на сервере |
| Локализация | next-intl | Русский сейчас, английский и украинский без переписывания компонентов |
| Графики | Recharts | Понадобится на этапе дашборда (этап 8); закладывается сразу, чтобы не менять стек позже |
| Excel | ExcelJS | Чтение для импорта и запись для выгрузки одной библиотекой, поддержка форматов ячеек |
| PDF | `@react-pdf/renderer` | Вёрстка отчёта на React, подключение кириллических шрифтов |
| Пароли | `@node-rs/argon2` | Argon2id — актуальная рекомендация OWASP, нативная скорость |
| Тесты | Vitest + Playwright | Модульные тесты прав и аудита; сквозные — на вход и работу с реестром |

Стек закрыт. Новая библиотека добавляется, только если задачу нельзя решить
имеющимися — с обоснованием в pull request.

## 3. Соглашения

### 3.1 Чтение и запись

- `queries.ts` — только чтение, возвращает данные для серверных компонентов.
- `actions.ts` — только мутации, помечены `"use server"`.
- Компоненты не обращаются к Prisma напрямую. Единственная точка входа к базе —
  `src/lib/db.ts`.

### 3.2 Каждый server action устроен одинаково

```ts
export const updateUser = authorizedAction(
  "users.update",                                   // 1–2. кто действует и имеет ли право
  async (actor, id: string, input: unknown) => {
    const parsed = updateUserSchema.safeParse(input); // 3. валидация
    // 4. запись + аудит в одной транзакции
    // 5. revalidatePath
  },
);
```

Порядок обязателен. Проверка прав идёт до валидации: чужому не следует сообщать,
что именно не так с данными, к которым у него нет доступа. `authorizedAction`
(`src/lib/auth/authorized-action.ts`) определяет пользователя и проверяет право
до вызова тела действия, поэтому пропустить эти шаги нельзя; отказ в праве
возвращается результатом, как и остальные ожидаемые ошибки (п. 3.3).

### 3.3 Ошибки

Ожидаемые ошибки (занятый логин, неверный пароль, нарушение правила) возвращаются
как результат: `{ ok: false, error: "users.loginTaken" }`, где значение — ключ
перевода. Исключения бросаются только на непредвиденных сбоях и приводят к
странице ошибки.

### 3.4 Состояние реестров

Поиск, фильтры, сортировка и номер страницы живут в параметрах URL, а не в
состоянии React. Это даёт работающие ссылки, кнопку «назад» и упрощает выгрузку —
экспорт получает те же параметры и отдаёт ровно то, что видит пользователь.

### 3.5 Тексты

Ни одной русской строки в коде. Ключи в `messages/ru.json` группируются по фичам:
`users.form.login`, `auth.errors.invalidCredentials`. Английский и украинский
добавляются копированием файла — структура ключей меняться не должна.

### 3.6 Именование в базе

Модели Prisma — единственное число в PascalCase (`User`, `AuditLog`), поля —
camelCase. Перечисления — SCREAMING_SNAKE_CASE.

### 3.7 Раздел «Настройки» из блоков

Раздел `/settings` (этап 2) — страница, собранная из независимых блоков. Каждый блок —
отдельная фича в `src/features/<блок>` со своими `queries.ts`, `actions.ts`, `schemas.ts`,
своими правами `settings.<блок>.*` и серверным компонентом блока. Страница раздела
проверяет `settings.read` и выводит по порядку блоки, на чтение которых у пользователя
есть право; сама она данных блоков не читает. Новый блок добавляется новой фичей и одной
строкой в списке блоков страницы.

Правка блока — в диалоге на странице раздела (клиентский компонент с react-hook-form),
а не на отдельном маршруте: так задано образцом в `ТЗ.md`, п. 5.7. После сохранения
action вызывает `revalidatePath("/settings")`.

Названия стран формы выводятся через `Intl.DisplayNames` на языке интерфейса — без
справочника и без новой библиотеки; при добавлении локалей (этап 10) они переводятся сами.

История изменений блока строится теми же средствами, что вкладка «История изменений»
в карточке пользователя: выборка `listEntityAuditLogs` (право на историю берётся из
карты `HISTORY_PERMISSION` по типу сущности) и таблица `AuditTable` из `features/audit`.
Копировать их в фичу блока нельзя.

### 3.8 Справочники и общие нидерландские проверки (этап 3)

Проверки и нормализация номеров KvK, btw-id, индекса, телефона и сайта, список стран
и форматирование адреса появились в `features/company` на этапе 2. На этапе 3 у них
появляются потребители в заказчиках, подрядчиках и проектах, поэтому они переносятся
в `src/lib/nl` без изменения поведения, вместе с фрагментом схемы Zod адреса (поля
и правило «целиком или никак»). Ключи переводов общих ошибок переезжают из
`settings.company.validation` в общий раздел `validation` файла `messages/ru.json`.
Копировать эти функции в фичу нельзя.

Справочники устроены как раздел пользователей: реестр на `DataTable` с состоянием в URL,
форма на отдельной странице, карточка со вкладками `UrlTabs`, история — `AuditTable`.
Запись справочника не удаляется, а переводится в архив (`isActive`).

**Выбор записи справочника в форме** (заказчик проекта, организация пользователя) —
список активных записей с поиском, который приходит в форму с сервера. Если сохранённая
запись уже в архиве, она добавляется в список выбранной с пометкой «в архиве». Действие
проверяет активность выбранной записи ещё раз на сервере — только когда значение
меняется, чтобы правка старого проекта с архивным заказчиком не отклонялась.

### 3.9 Закрытые записи и данные по ролям (этап 3)

**Закрытый проект.** Любое действие, меняющее проект или (с этапа 4) данные внутри него,
пишет с условием `status = IN_PROGRESS` в той же транзакции, что и аудит, и при нуле
изменённых строк возвращает `{ ok: false, error: "projects.errors.closed" }`. Отдельная
проверка статуса перед записью не заменяет условие: проект могут закрыть между чтением и
записью. Интерфейс по статусу только скрывает кнопки.

**Разные поля для разных ролей.** Выборка проектов строит `select` по правам пользователя:
без `projects.budget.read` поля бюджета не читаются из базы, без `projects.read` выборка
ограничена статусом «В работе» и полями, доступными подрядчику. Тип результата отражает
это явно (бюджет — необязательное поле), чтобы компонент не мог показать то, чего нет.
Колонки реестра и выгрузки строятся из того же набора прав — одним списком для экрана
и файла.

**Деньги и часы.** `Decimal` из Prisma не передаётся в клиентские компоненты напрямую:
выборка отдаёт строку с точным значением, формат `12 500,00 €` строится функциями
`src/lib/format.ts`, а в Excel сумма уходит числом с денежным форматом ячейки
(`format: "money"`). Сумма с НДС вычисляется одной функцией в `features/projects/budget.ts`
в целых центах, без арифметики с плавающей точкой.

### 3.10 Отчёты о работе (этап 4)

**Запись в проект.** Действия, вносящие, меняющие, удаляющие, утверждающие отчёт или снимающие
утверждение, выполняются в одной транзакции по порядку: строка проекта берётся
`SELECT … FOR SHARE` с условием `status = 'IN_PROGRESS' AND "deletedAt" IS NULL` (нет строки —
`projects.errors.closed`) → запись отчёта с условием по его статусу → аудит. Закрытие проекта
обновляет его строку первым (это блокировка, которая ждёт незавершённые записи отчётов),
затем считает неутверждённые отчёты и откатывается с их числом. Так правило п. 3.9 держится
и для данных внутри проекта, а отчёт, внесённый в момент закрытия, не проскакивает мимо
подсчёта (`СХЕМА-БД.md`, 10.4). Запрос с `FOR SHARE` — единственное место, где действие
отчётов пишет SQL сам (`$queryRaw`): Prisma не умеет блокировать строки.

**Чьи отчёты.** Выборки `features/reports/queries.ts` строят условие от прав: без `reports.read`
к любому запросу добавляется `userId = текущий пользователь`. Одна функция условия служит
реестру, итогам, вкладке проекта и выгрузке — так же, как у проектов (п. 3.9).

**Пересечения.** Их отклоняет исключающее ограничение базы. Действие перехватывает ошибку
`23P01` и возвращает ошибку поля со ссылкой на мешающий отчёт — его находит отдельный запрос
после отката. Та же проверка без записи — чистая функция `overlap.ts` — нужна только для
предпросмотра импорта: строки файла сравниваются между собой и с отчётами из базы.

**Время и часы.** Время хранится минутами от полуночи (`СХЕМА-БД.md`, 10.4). Разбор `ЧЧ:ММ`,
показ минут как времени и как десятичных часов (`7,50`) — функции `features/reports/time.ts`;
часы для показа округляются из суммы минут, а не складываются из округлённых значений.
Итоги считаются в SQL агрегатом `SUM("endMinute" - "startMinute" - "lunchMinutes")`.

**Форма на телефоне.** Форма отчёта — основной экран подрядчика: поля даты и времени —
стандартные `<input type="date">` и `<input type="time">`, чтобы телефон показывал свои
элементы выбора; поля в одну колонку до ширины 768 px.

### 3.11 Общий механизм импорта (этап 4)

`src/lib/import` — общая часть, которую этап 6 переиспользует без переделки. Это исключение
из правила «в `lib` — только то, у чего два потребителя» (п. 2): второй потребитель известен
заранее, и решение 18.09.2026 требует сразу общий механизм, а не перенос кода отчётов потом.

```ts
type ImportColumn<Row> = {
  key: keyof Row;
  header: string;                       // уже переведённый заголовок колонки файла
  type: "text" | "integer" | "date" | "time";
  required?: boolean;
};

type ImportDefinition<Row, Ready> = {
  name: string;                         // имя в аудите и в имени файла шаблона
  permission: Permission;               // "reports.import"
  columns: ImportColumn<Row>[];
  instructions: string[];               // лист «Инструкция» шаблона
  // Проверка всех строк сразу: пересечения внутри файла и с базой видны только целиком.
  check(rows: ParsedRow<Row>[], actor: SessionUser): Promise<RowResult<Ready>[]>;
  // Запись готовых строк внутри переданной транзакции, вместе с аудитом.
  write(tx: Tx, ready: Ready[], options: Record<string, boolean>, actor: SessionUser): Promise<void>;
};
```

- **Разбор** — ExcelJS (уже в стеке): первый лист, заголовки в первой строке, колонки по
  названию; ячейки-даты, ячейки-время и текст `дд.ММ.гггг` / `ЧЧ:ММ` приводятся к одному виду;
  пустые строки пропускаются; номер строки файла сохраняется для сообщений.
- **Без промежуточного хранения.** Предпросмотр ничего не пишет в базу. Файл остаётся в
  браузере; «Подтвердить» отправляет его ещё раз вместе с опциями, сервер заново разбирает и
  проверяет его и, если все строки готовы, пишет их одной транзакцией. Если результат проверки
  изменился (появились ошибки), запись не выполняется, возвращается новый предпросмотр.
  Таблица-черновик импорта не нужна: нет данных, которые надо чистить, и нет разрыва между
  тем, что проверено, и тем, что записано.
- **Лимиты:** файл до 5 МБ и до 2 000 строк с данными. Файл передаётся в server action
  через `FormData`; лимит тела server actions поднимается в `next.config.ts`
  (`experimental.serverActions.bodySizeLimit`) до 6 МБ, а размер ещё раз проверяется в действии.
- **Шаблон** строится из того же описания колонок: `/api/import/template?name=reports`
  отдаёт `.xlsx` с листом данных и листом «Инструкция»; право — то же, что у импорта.
- Каждый импорт пишет одну запись `IMPORT` (имя файла, число записей, опции); записи
  о созданных объектах пишет `write` своего раздела.

### 3.12 Поля с отдельным правом на просмотр (этап 4)

До этапа 4 история проекта скрывала бюджет по списку `PROJECT_BUDGET_FIELDS` в
`features/audit/queries.ts`. С этапа 4 это правило задаётся в описании полей сущности для
журнала — там же, где читаемые названия и форматирование значений: у поля указано право,
без которого его значение не показывается (`projects.budget.read` у `budgetAmount`, `vatRate`,
`budgetHours`). Пометки лежат рядом со снимком сущности для журнала (`PROJECT_AUDIT_FIELDS` в `features/projects/audit.ts`) и собраны по сущностям в `features/audit/fields.ts`; поля с одним `withheldAs` показываются без прав одной строкой («Бюджет: изменён»). Выборка истории и журнала скрывает поля по этим пометкам. Модульный тест
(`tests/unit/audit-fields.test.ts`) проходит по полям моделей Prisma — в Prisma 7 `Prisma.dmmf` не экспортируется, описание моделей берётся у клиента: поле типа `Decimal` без пометки и без явного «не
финансовое» роняет тест — новое денежное поле не попадёт к сотруднику незамеченным.
Бюджет часов проекта — поле с правом, поэтому и сравнение итогов отчётов с ним показывается
только при `projects.budget.read`.

## 4. Аутентификация

Применяется схема с непрозрачным токеном и таблицей сессий (подход Lucia),
а не JWT.

Причина: по ТЗ администратор обязан **немедленно** прекращать доступ
деактивированного сотрудника. Подписанный токен нельзя отозвать до истечения
срока, а проверка в базе на каждом запросе сводит на нет его единственное
преимущество. Таблица сессий сразу даёт и отзыв доступа, и экран «Активные
сессии», требуемый ТЗ.

Механика:

1. При входе генерируется случайный токен (32 байта), в базе хранится его хэш.
2. Токен кладётся в httpOnly-cookie `session` с `SameSite=Lax`, срок — 12 часов.
3. На каждом запросе `middleware.ts` проверяет наличие cookie и перенаправляет
   неавторизованных на `/login`; серверная проверка самой сессии и роли
   выполняется в `requireUser()` — middleware к базе не обращается.
   Если cookie есть, а сессия отозвана или истекла, страница перенаправляет на
   `/api/auth/clear-session`: Server Components не могут менять cookie, поэтому её
   удаляет route handler и уже он ведёт на `/login`. Server actions вызывают
   `requireActionSession()` и удаляют cookie сами: цель редиректа из action Next.js
   рендерит на сервере, и cookie из промежуточного ответа до браузера не дошла бы.
4. Сессия с активностью в последний час продлевается автоматически.
5. Деактивация пользователя и сброс его пароля администратором отзывают сессии.

Защита от подделки межсайтовых запросов обеспечивается механизмом server actions
Next.js и флагом `SameSite`; отдельный слой не вводится.

## 5. Экспорт

Единый модуль `src/lib/export` принимает описание колонок и набор данных:

```ts
type ExportColumn<T> = {
  key: keyof T;
  header: string;                      // уже переведённый заголовок
  width?: number;                      // в символах; по умолчанию — по самому длинному значению
  format?: "text" | "number" | "money" | "date" | "datetime";
};
```

На вход подаются те же параметры фильтрации, что и у реестра, поэтому выгрузка
всегда соответствует тому, что пользователь видит на экране. Три формата —
`xlsx`, `pdf`, представление для печати — реализуются поверх одного описания.
Разделы следующих этапов подключают экспорт, лишь описав свои колонки.

**Подключение раздела.** Раздел описывает выгрузку в `features/<раздел>/export.ts`
через `defineExportReport`: имя отчёта (оно же начало имени файла), путь реестра, право
(`users.export`), тип сущности для аудита и функцию `load`, которая по параметрам URL
реестра возвращает название отчёта, колонки и строки. Значения в строках уже читаемые —
название роли, а не её код. Отчёт вносится в список `features/export/reports.ts`, кнопки
`ExportButtons` ставятся на страницу реестра — больше ничего не требуется.

**Те же строки, что на экране.** Выборка для выгрузки (`listUsersForExport`,
`listAuditLogsForExport`) строится теми же функциями условий и сортировки, что и выборка
реестра, но без пагинации: в файл попадают все страницы отфильтрованного списка.

| Формат | Адрес | Реализация |
|---|---|---|
| Excel | `/api/export/xlsx?report=users&…` | ExcelJS: закреплённая строка заголовков, автоширина колонок; даты — датами в стенном времени `Europe/Kyiv` (в ячейке нет часового пояса), числа — числами |
| PDF | `/api/export/pdf?report=users&…` | `@react-pdf/renderer`: A4 альбомная; шапка с названием, датой выгрузки и автором, строка заголовков таблицы и номер страницы повторяются на каждой странице |
| Печать | `/print/users?…` | Отдельная страница вне общего layout: `@page` A4 альбомная, `<thead>` повторяется на каждом листе, строки не разрываются между листами; диалог печати открывается сразу |

- Кнопки выгрузки показываются по праву отчёта и сделаны обычными ссылками, а не
  `next/link`: предзагрузка открыла бы печатное представление и записала выгрузку,
  которой не было.
- Право проверяется дважды: маршрут без права ведёт на «Доступ запрещён», а выборка
  отчёта сама вызывает `requirePermission`.
- Отчёт может ограничить параметры функцией `checkParams`, возвращающей ключ перевода
  причины отказа. Тогда кнопки неактивны и показывают причину, маршрут файла отвечает 400,
  печатное представление выводит сообщение, а выборка проверяет условие ещё раз сама.
  Так журнал аудита выгружается за период не длиннее календарного месяца
  (`features/audit/schemas.ts`, `ТЗ.md`, п. 4.11).
- **Лимит строк PDF и печати** (с этапа 4, `ТЗ.md`, п. 4.11): общий для всех отчётов — не
  больше 2 000 строк. Выборка сначала считает строки (`count` с теми же условиями); при
  превышении кнопки PDF и печати неактивны с подсказкой, маршрут PDF отвечает 400, печатное
  представление выводит сообщение. Excel лимита не имеет. Проверка встроена в общий модуль,
  а не в `checkParams` каждого отчёта: новый реестр получает её без кода.
- **Итоговая строка** (с этапа 4): отчёт может вернуть вместе со строками `totals` — значения
  для части колонок; Excel, PDF и печать выводят их последней строкой «Итого». Суммы считает
  выборка (в SQL), а не модуль экспорта — он не знает, какие колонки складываются.
- Каждая выгрузка, в том числе печатное представление, пишется в аудит как `EXPORT`
  (`СХЕМА-БД.md`, 4.3) — после того как файл собран, чтобы сбой не оставлял записи.
- Имя файла — `<отчёт>_<дата выгрузки>`: `users_14.09.2026.xlsx`.
- Стандартные шрифты PDF не содержат кириллицы, поэтому в `lib/export/fonts` лежит
  Inter (SIL Open Font License 1.1, текст — `OFL.txt`): в нём есть и кириллица, и стрелка
  «→» из журнала изменений, которой нет, например, в PT Sans. Путь к шрифтам строится
  от корня проекта.
- fontkit хранит прочитанные глифы в загруженном шрифте. Встроив в документ составной глиф
  (кириллическая «С» рисуется глифом латинской «C»), он запоминает компонент без символа,
  и следующий документ теряет эту латинскую букву. Поэтому `renderPdf` загружает шрифты
  заново перед каждым документом и собирает документы по одному.
- Служебные поля не выгружаются: выборки не читают хэши, а из журнала не выгружается
  идентификатор объекта — у сессии это идентификатор сессии.

## 6. Локальный запуск

```bash
cp .env.example .env          # задать POSTGRES_PASSWORD и SEED_ADMIN_PASSWORD
docker compose up -d db       # PostgreSQL 16 на порту 5432
npm install
npx prisma migrate dev        # схема и миграции
npm run db:seed               # первый администратор
npm run dev                   # http://localhost:3000
```

Сид создаёт единственную учётную запись `admin` с паролем из переменной
`SEED_ADMIN_PASSWORD`. Пароля по умолчанию в коде нет — при незаданной переменной сид завершается
с ошибкой.

**Скрипты:** `dev`, `build`, `start`, `lint`, `typecheck`, `test`, `test:e2e`,
`test:db:init`, `db:seed`, `db:studio`.

## 7. Что должно оставаться расширяемым

Решения этапов 1–4, на которые обопрутся следующие разделы, — менять их потом дорого:

1. **Аудит** — универсален по типу сущности (`entity` + `entityId`), поэтому
   сведения о компании, заказчики, подрядчики и проекты подключаются без изменения таблицы.
2. **Права** — заданы строками вида `users.update`; добавление раздела означает
   добавление строк в матрицу, а не переписывание проверок.
3. **Экспорт** — работает с описанием колонок, а не с конкретной моделью.
4. **Локализация** — все тексты вынесены с самого начала.
5. **Поля аудита в таблицах** — `createdById` и `updatedById` заводятся сразу
   в каждой новой модели, иначе отметку «кем изменено» придётся добавлять
   задним числом по всей базе.
6. **Запрет изменений закрытого проекта** — условие записи, а не проверка в интерфейсе
   (пп. 3.9–3.10): отчёты этапа 4 подключены к нему, расходы этапа 5 подключаются так же.
7. **Импорт** — общий механизм с описанием колонок и функциями проверки и записи (п. 3.11):
   этап 6 подключает к нему остальные данные, не меняя загрузку, предпросмотр и транзакцию.
8. **Поля с правом на просмотр** — пометка в описании полей сущности (п. 3.12), а не список
   рядом с выборкой: расходы этапа 5 помечают свои суммы тем же способом.
