# Права доступа — этап 1

## 1. Главное правило

**Право проверяется на сервере в каждом server action и в каждом запросе данных.**
Скрытая в интерфейсе кнопка — удобство для пользователя, а не защита: любой
запрос можно повторить в обход интерфейса.

Порядок в каждом действии: определить текущего пользователя → проверить право →
проверить входные данные → выполнить. Проверка права идёт **до** валидации:
пользователю без доступа не следует сообщать, что именно не так с данными.

сотрудник и подрядчик свой профиль только просматривают (`ТЗ.md`, п. 4.8). Логин не
меняется вообще (`ТЗ.md`, п. 4.5), роль меняет только администратор в форме пользователя
(`users.changeRole`). Свой пароль пользователь не меняет: пароли назначает и сбрасывает
только администратор (`users.resetPassword`).

## 3. Правила, не выражаемые матрицей

Проверяются отдельно, после проверки права:

1. **Нельзя деактивировать или понизить в роли последнего активного
   администратора.** Проверка выполняется в транзакции — иначе два одновременных
   запроса способны снять обоих оставшихся администраторов.
2. **Нельзя деактивировать самого себя.** Право у администратора есть,
   но действие отклоняется.
3. **Профиль администратора правит только администратор.** Менеджер правит ФИО,
   должность, email и телефон остальных пользователей, в том числе других менеджеров;
   роль, статус, комментарий, пароль и сессии других пользователей ему недоступны.
   Нужное право зависит от роли того, чей профиль правится, поэтому действие проверяет
   его после чтения записи: `requirePermission(actor, userUpdatePermission(target))`.
4. **Сотрудник и подрядчик не имеют доступа к `/users` и `/audit`.** Переход по
   прямой ссылке приводит к странице «Доступ запрещён», а не к пустому реестру.
   Свой профиль они только просматривают и завершают в нём свои сессии.
5. **Деактивированный пользователь не входит в приложение**, а его активные сессии
   прекращаются немедленно при деактивации.
6. **Пользователей не удаляет никто.** Операции удаления учётной записи нет ни
   у одной роли — только деактивация (`ТЗ.md`, п. 4.7).
7. **История изменений в карточке не открывает журнал.** Менеджер видит на вкладке
   «История изменений», кто, когда и что изменил, но `/audit` ему недоступен. IP-адрес
   и браузер записей истории отдаются только роли с `audit.read`: чужие сессии
   менеджеру не показываются (`users.sessions.read`), поэтому и в истории их данных нет.

## 4. Реализация

Права описываются строками и матрицей в `src/lib/permissions.ts`:

```ts
export const PERMISSIONS = {
  ADMIN:      ["users.*", "audit.*", "profile.*"],
  MANAGER:    ["users.read", "users.history.read", "users.updateProfile", "users.export", "profile.*"],
  EMPLOYEE:   ["profile.read", "profile.sessions"],
  CONTRACTOR: ["profile.read", "profile.sessions"],
} as const;

export function can(user: SessionUser, permission: Permission): boolean;
export function requirePermission(user: SessionUser, permission: Permission): void;
// "users.update" для администратора, "users.updateProfile" для остальных
export function userUpdatePermission(target: { role: Role }): Permission;
```

`requirePermission` бросает `PermissionDeniedError`, которая наверху превращается в
страницу «Доступ запрещён» либо в отказ действия — в зависимости от того, пришёл
запрос за страницей или за мутацией:

- **Страница** раздела начинается с `requirePagePermission(permission)`
  (`src/lib/auth/current-user.ts`): пользователь без права перенаправляется на
  `/forbidden` ещё до чтения данных.
- **Server action** объявляется через `authorizedAction(permission, action)`
  (`src/lib/auth/authorized-action.ts`): пользователь и право проверяются до разбора
  аргументов, отказ возвращается результатом `{ ok: false, error: "errors.forbiddenAction" }`.
  Права, зависящие от данных (правка администратора, смена роли, статуса и комментария
  в форме редактирования), проверяются внутри действия тем же `requirePermission`
  и дают тот же отказ.
- **Выборка** в `queries.ts` принимает текущего пользователя и тоже вызывает
  `requirePermission`: страница, в которой забыли проверку, упадёт с ошибкой,
  а не покажет данные.

Интерфейс использует ту же функцию `can()`, чтобы не показывать недоступное.
Дублировать правила отдельным списком для UI нельзя: два списка неизбежно
разойдутся.

## 5. Добавление раздела в следующих этапах

Новый раздел означает добавление строк прав (`projects.read`, `projects.create`, …)
в матрицу и вызовы `requirePermission` в его действиях. Переписывать механизм
проверки не требуется — это и есть причина, по которой права заданы строками,
а не набором булевых полей у роли.

## 6. Что проверять при приёмке

- Менеджер открывает `/users`, но не видит кнопок создания, сброса пароля и
  деактивации; «Редактировать» есть у всех, кроме администраторов, и форма открывает
  ему только ФИО, должность, email и телефон.
- Менеджер, открыв `/users/[id]/edit` администратора, получает «Доступ запрещён»;
  прямой вызов правки администратора или комментария отклоняется сервером.
- Сотрудник и подрядчик открывают `/profile` без формы правки; администратор
  и менеджер правят в нём свои данные.
- Менеджер видит в карточке вкладку «История изменений» без IP-адресов и браузеров,
  а `/audit` для него закрыт.
- Прямой вызов действия создания пользователя от имени менеджера отклоняется
  сервером, а не только скрыт в интерфейсе.
- Сотрудник и подрядчик при переходе на `/users` и `/audit` получают
  «Доступ запрещён».
- Попытка понизить роль последнего администратора отклоняется с понятным
  сообщением.
- Попытка администратора деактивировать самого себя отклоняется.
