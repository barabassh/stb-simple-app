# ConstructionProjects — правила работы над проектом

Учётная система строительных проектов. Данные вводятся через формы и импорт Excel,
выводятся в таблицы с фильтрами и на дашборд, выгружаются в Excel/PDF и на печать.

**Источник истины по требованиям — `docs/ТЗ.md`.** Перед любой задачей читай раздел ТЗ,
относящийся к текущему этапу. Если требование в коде расходится с ТЗ — расхождение
нужно обсудить, а не «дореализовать по своему усмотрению».

## Стек

Next.js 15 (App Router) · React 19 · TypeScript (strict) · PostgreSQL 16 · Prisma ·
Tailwind CSS · shadcn/ui · TanStack Table · Zod · react-hook-form · next-intl ·
Vitest · Playwright.

Детали и структура папок — `docs/АРХИТЕКТУРА.md`.

## Язык

- **Интерфейс, тексты ошибок, письма, названия колонок в экспорте — русский.**
- **Код, имена переменных, комментарии, коммиты, имена файлов — английский.**
- Ни одной русской строки в JSX или в коде server actions. Все пользовательские
  тексты — через `next-intl` из `messages/ru.json`. Планируются английский и
  украинский, поэтому хардкод текста ломает следующий этап.

## Работа с данными

- Чтение — в `src/features/<feature>/queries.ts`, запись — в `actions.ts`
  (server actions). Компоненты не обращаются к Prisma напрямую.
- Каждая мутация проходит три шага: проверка прав → валидация Zod → запись + аудит.
  Пропуск любого из них — ошибка, даже если кнопка в UI скрыта от этой роли.
- Права проверяются **на сервере в каждом action**. Скрытие кнопки в UI — удобство,
  а не защита. Матрица прав — `docs/ПРАВА-ДОСТУПА.md`.
- Каждое изменение данных пишется в `AuditLog` через `src/lib/audit`.
  Пароли, хэши и токены сессий в аудит не попадают никогда.
- Схемы Zod лежат в `schemas.ts` рядом с фичей и используются и клиентом, и сервером —
  дублировать правила валидации нельзя.

## Схема базы данных

- Изменения схемы — только через миграции Prisma (`npx prisma migrate dev --name ...`).
  Не редактировать применённые миграции и не делать `migrate reset` на данных,
  которые мог заполнить пользователь, без явного разрешения.
- Все содержательные таблицы получают `createdAt`, `updatedAt`, `createdById`,
  `updatedById`. Удаление — мягкое (`deletedAt`), чтобы ссылки из аудита не ломались.
  Пользователи не удаляются вовсе — только деактивируются (`isActive = false`).
- Подробности — `docs/СХЕМА-БД.md`.

## Форматы и локаль

- Дата и время: `dd.MM.yyyy HH:mm`. Только дата: `dd.MM.yyyy`.
- Таймзона отображения — `Europe/Kyiv`; в базе всё хранится в UTC.
- Числа: разделитель разрядов — неразрывный пробел, десятичный разделитель — запятая.
- Деньги — `Decimal` в Prisma, никогда не `Float`.

## UI

- Вёрстка адаптивная (ТЗ п. 3.2): экраны проверяются на ширине 1280, 768 и 360 px.
  Страница не прокручивается по горизонтали — прокручиваются только таблицы внутри
  своего блока.
- Server Components по умолчанию. `"use client"` — только там, где нужен
  интерактив (формы, фильтры, таблицы).
- Компоненты shadcn/ui из `src/components/ui` не переписываются под конкретный
  экран — нужна вариация, значит нужен проп или обёртка.
- Списки: серверная пагинация, сортировка и фильтрация через search params, чтобы
  состояние таблицы жило в URL и его можно было переслать ссылкой.

## Перед завершением задачи

```bash
npm run lint
npm run typecheck
npm test
```

Всё три должны проходить. Если задача касалась UI — запусти `npm run dev`
и проверь сценарий в браузере; не сообщай о готовности функции, проверив только типы.

## Чего не делать

- Не добавлять функциональность следующих этапов «заодно». Границы этапа — в `docs/ТЗ.md`,
  план развития — в `docs/РОАДМАП.md`.
- Не вводить новые библиотеки без необходимости: стек зафиксирован в `docs/АРХИТЕКТУРА.md`.
- Не писать комментарии, пересказывающие код. Комментарий уместен только там, где
  неочевидно **почему** так сделано.
- Не создавать промежуточные файлы с планами и отчётами в репозитории.
